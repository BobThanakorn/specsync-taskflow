# ADR-002: SQL query-parameter filtering for GET /tasks

- Status: Accepted
- Date: 2026-09-25
- Deciders: TaskFlow core team
- Relates to: [ADR-001](ADR-001.md), PRD R-11

## Context

PRD requirement R-11 calls for `GET /tasks` to support optional filtering by
`status`, `priority`, and a case-insensitive substring search on the task
title (`q`). Multiple filters must be combinable in a single request.

Three implementation strategies were considered:

1. **SQL `WHERE` clauses built at query time** — append conditions to a base
   SQL statement depending on which parameters are present.
2. **Full-text search (FTS5)** — create a SQLite FTS5 virtual table and use
   `MATCH` queries for title search.
3. **In-process filtering** — fetch all rows from SQLite, then filter the
   Python list before returning.

## Decision

Implement filtering with **dynamically composed SQL `WHERE` clauses** (option 1).

- `status` and `priority` use exact-match (`= ?`) conditions.
- `q` uses `LOWER(title) LIKE LOWER(?)` with `%q%` wildcards, giving
  case-insensitive substring matching without any additional schema objects.

The implementation lives in
[`app/routers/tasks.py::list_tasks`](../app/routers/tasks.py).

## Rationale

### Why not FTS5?

SQLite FTS5 provides fast full-text search but carries meaningful overhead for
this use case:

- Requires a separate virtual table and a synchronisation trigger or manual
  insert into the FTS index on every write.
- FTS5 `MATCH` semantics (tokenisation, stemming) differ from simple substring
  matching — a search for `"read"` would not match `"README"` without tuning.
- The PRD requirement is explicitly a *substring* match, not ranked full-text
  relevance. FTS5 is over-engineered for this.
- Adds schema complexity that is hard to reverse without a migration.

### Why not in-process filtering?

Fetching all rows and filtering in Python is simple but does not scale. Even
for a small-team tool, loading every task on every filtered request wastes
memory and I/O. Pushing filtering into the SQL layer keeps the approach
idiomatic with the rest of the codebase (raw SQLite, no ORM).

### Why SQL `WHERE` clauses?

- **Zero additional schema objects** — no new tables, triggers, or virtual
  tables are required.
- **Correct semantics** — `LIKE` with `LOWER()` on both sides delivers the
  exact case-insensitive substring behaviour described in the PRD.
- **Composable** — conditions are accumulated in a list and joined with `AND`,
  so any combination of filters works without special-casing.
- **Consistent with ADR-001** — the existing codebase uses raw SQLite
  connections with hand-written SQL throughout; this approach requires no new
  dependencies and follows the same pattern.
- **Upgradeable** — if the project migrates to PostgreSQL (see ADR-001
  consequences), the same `LOWER(column) LIKE LOWER(?)` pattern works
  unchanged, or can be replaced with `ILIKE` with a one-line change.

## Consequences

- **Positive:** no schema changes; implementation is ~20 lines; easy to
  reason about and test.
- **Positive:** `q` behaves as a pure substring match — predictable for users.
- **Negative:** `LIKE '%q%'` cannot use a B-tree index (leading wildcard).
  For datasets of tens of thousands of tasks this may become slow. If that
  threshold is reached, adding an FTS5 index or moving to PostgreSQL
  `pg_trgm` is the recommended migration path.
- **Neutral:** `status` and `priority` filters hit the `status` column
  directly; an index on `status` would improve performance at scale but is
  not required at the current scope.
